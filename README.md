# TestBuddy demo

[![Java 21+](https://img.shields.io/badge/Java-21%2B-blue)](https://openjdk.org/)

A two-module Maven project with the same `Shipment` class, once in a core library and once in a Spring project.
Use it to see how TestBuddy's output changes with the validation setup, and to check your IDE setup.

## The class

`Shipment` prices a parcel. Its rules are the same in both modules:

| Field | Rule | Meaning |
|---|---|---|
| `weightKg` | `@Positive` | a parcel weighs more than zero |
| `deliveryDays` | `@Min(1) @Max(30)` | delivery takes 1 to 30 days |
| `discountPercent` | `@Min(0) @Max(100)` | a discount from 0 to 100 percent |

| Member | Kind | Generated test |
|---|---|---|
| `Shipment(...)` constructor | creation | creation and field tests |
| `getWeightKg()`, `getDeliveryDays()`, `getDiscountPercent()` | getters | returns a value, same value on repeat calls |
| `shippingCost()` | query, returns `double` | **TODO**: the expected value is not known yet |
| `isExpress()` | query, returns `boolean` | **TODO**: the expected value is not known yet |

The two modules differ only in how the rules are enforced:

- **core-demo** has no validation provider. The constructor throws `IllegalArgumentException` for a value outside a rule,
  and the generated tests expect that exception.
- **spring-demo** has Spring Boot's validation starter (Hibernate Validator) on the test classpath, and TestKit is told
  the project type is Spring. The constructor accepts any value, and the generated tests ask the validator for a
  violation. In a real Spring app, the same rules are checked at `@Valid` boundaries such as controllers.

## Run the tests

```bash
mvn test
```

The build is **expected to fail** on the first run. Each module has two `testReturnsResult` tests, for `shippingCost()`
and `isExpress()`, that fail with a `TODO` message. TestBuddy cannot know the correct result of a method, so it leaves
the expectation for you to write. Until you do, the test fails and never passes silently.

To see one pass, replace the TODO in `ShipmentMethodShippingCostTest` with the expected value. The fixture is
`new Shipment(1.5d, 15, 1)`, so the cost is 1.5 × 2.5 × 99 / 100 = 3.7125:

```java
import static org.assertj.core.api.Assertions.within;

assertThat(result).isEqualTo(3.7125, within(1e-9));
```

Generated code keeps the `Generated by TestKit` header. Put your own tests in a separate file, such as
`ShipmentExtraTest.java`, so regeneration does not overwrite them.

## Generate the tests with TestBuddy

1. Open the project in IntelliJ and let it build once.
2. Right-click `Shipment.java` in each module → **TestBuddy → Generate Test**.
3. Compare the two generated files: `com/paramichha/demo/core/ShipmentTest.java` and `com/paramichha/demo/spring/ShipmentTest.java`.

With Pro, you can also enable **Always split** and change the naming in **Settings → Tools → TestBuddy**, and
compare the split output with the single file.

The committed files were generated with TestKit's seed 42. Generated values depend on the seed, so files from your
IDE will differ in the values but not in the structure.

## Compile with `-parameters`

This project sets `-parameters` in `pom.xml`, so constructor and method parameter names survive compilation.
TestBuddy and TestKit use those names to match a rule to its parameter. For this demo the generated tests are the
same with or without the flag, but a class whose constructor parameter names differ from its field names needs it.

If you build the classes in IntelliJ, you can add it there too:

**Settings → Build, Execution, Deployment → Compiler → Java Compiler → Additional command line parameters:**
`-parameters`

## What to look for

- **Core module:** the constructor is the only check, so the rejects tests call the constructor and expect an exception.
  A failure message names the field and what to fix.
- **Spring module:** the constructor accepts any value, so the rejects tests ask the validator for a violation on
  each field. A field without the annotation fails its test.
- **Both:** the field tests, the creation tests and the getter tests pass as soon as the class is correct.
